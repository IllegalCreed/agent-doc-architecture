1. 本文 §2「核心前提」——全系列唯一论点，所有章节都从它推导；

## 1. 目标与产出

把一个真实大型项目 7 个月的 AI 协作文档实践，提炼成：

1. **技术博客系列（4 篇，每篇 5–6 千字，中文）**；
2. **Skill**：系列定稿后提炼，发布在本仓库 `skill/`；分两种模式——**新项目初始化**（只有稳态规则，无冻结区、无基线）与**存量项目接入**（额外生成接入配置：冻结区、规则生效日期、豁免基线）；
3. **反哺源项目**：写作中发现的源项目文档缺陷（§6）在源项目内以 D 类变更治理，治理前后对比再回流为③④篇证据。

闭环：实践 → 总结（博客）→ 治理（源项目）→ 再总结（③④篇 + skill）。

## 2. 核心前提：Agent-first 文档

**文档的第一读者是 Agent。** 整套机制都是基于这一点设计的；文章中每条原则都必须能回溯到下表中 Agent 的某个特性。

| Agent 特性 | 对文档的要求 | 对应机制 |
|---|---|---|
| 无跨会话记忆 | 每次从入口进，入口必须是路由表 | L0 + 「操作 → 必读」表 |
| 上下文有限且有成本 | token 是第一成本，按需下钻 | L0–L3 分层、薄索引 |
| 按字面执行、不会意会 | 状态、替代关系、适用范围显式写出；「建议参考」改为「执行前必须先读」 | 状态机、`Replaced by`、必读表 |
| 能 grep / glob / 跑脚本 | 命名可模式匹配、元信息可解析、规则可 lint | 编号体系、元信息块、doc-lint |
| **同时是主要作者** | 约定靠自觉必漂移，必须机器强制 | hook / CI 校验 |
| 多个 Agent 并存 | 单一入口；教训进 repo 而非个人记忆 | 唯一入口文件（AGENTS.md） |

**代码、测试、文档三者同等重要，缺一不可。** AI 时代的项目里，代码由 Agent 写，测试证明代码对，文档告诉 Agent 该怎么写、写完往哪回写。三者互相咬合：路由表把 Agent 引向测试规范；用例索引把测试反向关联到需求；doc-lint 就是「文档的测试」。本系列是其中「文档」这条腿；测试另有专题系列（见 §10）。

推论（各篇共用）：

- **人的角色从读者变为裁决者**：批准 plan、拍板、封板验收、确认交付物；人读 Agent 为裁决点产出的摘要、diff 和对话总结，不翻文档树、不维护文档。
- **交付物 ≠ 工程文档**：用户手册、更新日志、部署交接说明的读者是业务用户/运维，属产品交付物；由 Agent 维护，但不进 Agent 路由体系，路由表只登记「何时必须更新它」。
- **一份文档只服务一种读者**：同时服务人和 Agent 的文档必然变胖（索引被当成进度看板写成段落）。索引只给 Agent；人看进度由 Agent 现场汇总或脚本生成视图。
- **L0 保留一句话理由**：理由让 Agent 能在边界情况下推断正确做法；完整实案下沉 L2/L3，只留链接。

## 3. 系列结构

按**机制**横切（不按文档类型、不按任务时间线）。所有文档类型（需求、设计、开发规范、重构、测试、封板、用户手册、DB 变更、部署、事故）在每篇中平等取例。

| 篇 | 回答的问题 | 写作依赖 |
|---|---|---|
| ① 总模型 | Agent 为什么「失忆」；文档为什么是路由系统 | 无 |
| ② 路由 | 该读哪几份 | 无 |
| ③ 寻址 | 去哪找、信哪份 | 源项目治理落地 |
| ④ 生命周期 | 写到哪、怎么不烂 | 源项目治理落地 |

**每篇统一结构**（也是 skill 模块骨架）：

1. 开场真实实案；
2. 症状 → 根因；
3. 原则 1–3 条，每条一句话可复述，并标注对应 §2 中的 Agent 特性；
4. 机制：目录/表头/规则模板片段；
5. 跨文档类型对照表（含「人的角色」列）；
6. 本机制自身会怎么坏；
7. 小结。

## 4. 四篇大纲

### ① 《Agent 不是失忆，是找不到入口——大型项目文档分层设计（一）》

1. 开场（中性叙述，只写文档与提交能证明的事）：09-16 同日封了两版（封板由 Agent 执行，原大纲口径）；09-18 立规提交补了封板规范、「操作 → 必读」表和两版漏写的 release 文档，立规文本注明教训是「封板未读全量定义、漏写 release 文档」；六套全量定义早已写在项目测试规范里，只是从入口出发没有任何一处路标把封板引向它（§5.3「封板漏读」「不可达的准确口径」「封板立规提交」）。
2. 范式转变：文档的第一读者是 Agent（§2 全表）；人的新角色；交付物边界。
3. 症状清单：不知道读哪份就不读；读到过期 plan 当事实；读太多被历史淹没；用例找不到来源需求；干完不回写；多 Agent 各读各的入口。
4. 根因：没有区分「常驻」与「按需」、「当前事实」与「历史」；入口文件成了百科全书而不是路由表。
5. 总模型：

   | 层 | 内容 | 何时读 | 约束 |
   |---|---|---|---|
   | L0 常驻 | 入口文件硬约定 + 路由表 | 每次会话自动加载 | 必须短 |
   | L1 按工作类型 | 规范（开发/测试/DB/封板/手册/部署） | 开工前按路由表只读一份 | 通用层 + 项目层 |
   | L2 按模块/变更 | plan bundle、长期专题、交接文档 | 进入该模块时 | 有状态、有替代关系 |
   | L3 证据 | 执行证据（封板测试报告、审计输出、事故报告） | 需要证据时下钻 | 不承担入口职责 |

   L3 只收执行证据；更新日志、交接说明（release 两件）与用户手册是交付物，不在 L0–L3 里。

   三个问题映射后三篇：读哪份 → ②；去哪找、信哪份 → ③；写到哪、怎么不烂 → ④。
6. 演进时间线（§5.2）：体系是被事故逼出来的，不是一开始设计好的。
7. 跨类型对照表：各类文档属于哪层、谁读、何时读、人的角色。
8. 会怎么坏：L0 膨胀；层级边界模糊（留给④）。
9. 小结 + 系列导航。

### ② 《让 Agent 只读该读的——文档路由设计（二）》

1. 开场：规范早就有，但从入口不可达——09-18 之前，「六套全量」的定义写在项目测试规范里，入口文件关于发版只有 Git 分支约定里一段打 tag 规则，没有任何一处提到「全量」或「封板」（§5.3「封板漏读」）。立规当天把封板规范接进入口文件的「操作 → 必读」表；截至 2026-10-14，此后 v2.0.5 至 v2.3.1 共 9 个版本，更新日志与交接说明两件齐全，v2.1.0 起每版都有封板测试报告（§5.3「立规后」）。路由失败不是「被淹没」，而是「根本没有路」。（「不可达」的严格口径是「从封板这件事出发不可达」：引用图上有两条两跳弱路径，一条路标写的是别的事，一条停在历史实例上，都没有把封板引向测试规范，见 §5.3「不可达的准确口径」。）
2. 原则：入口文件只路由不承载；按「工作类型」路由而非「目录」路由；每一跳都声明下一跳和自己的上层（我是谁的子集）。
3. 机制 1「操作 → 必读」路由表：形态（操作｜必读规范｜一句话要点）；收录高风险、低频、凭印象易错的操作，不收日常编码；一句话要点保证没跳转也拿到最关键约束。
4. 机制 2 多 Agent 统一入口：CLAUDE.md 涨到 406 行后改为 AGENTS.md 唯一、CLAUDE.md 只转发；个人 memory 只放协作偏好，通用教训进 repo。
5. 机制 3 通用 → 项目两层继承：通用层留占位项；项目层首行声明继承，只写填充、现状、例外和本项目坑。正面样板：移动端测试落地说明；反面：§6 #12。
6. 机制 4 逐级路由链：入口 → docs/README（按职责）→ 一级目录 README（二级路由 + 放置规则）→ 文档开头 AI Quick Path → 正文。
7. 机制 5 交接文档是一次性路由：handoff 写明先读什么、每次交审附哪些证据。
8. 跨类型对照表：需求/开发/重构/测试/封板/手册/DB/部署/代码审查/浏览器调试 → L1 入口、通用层、项目层、下一跳、人的角色。
9. 会怎么坏：路由表长成入口文件本身；指向已被替代的文档；项目层不声明继承（#12）。
10. 小结。

### ③ 《让每份文档都有唯一的位置——文档寻址设计（三）》

1. 开场：测试资料散在 4 处、plan 根目录多种分法并列，Agent 靠猜文件名；一次信息架构重整动了 235 个文件。
2. 原则：按职责分目录不按类型/状态分（完成不挪位置，路径稳定优先）；一个事实一个源，其余是派生视图；状态写在文档里不靠目录表达。命名统一的理由是机器可匹配，不是美观。
3. 机制 1 职责目录 + 每目录「放置规则」表。
4. 机制 2 稳定编号体系（最适合抽 skill 模板）：
   - 变更 `<T>-YYYYMMDD-NNN` ↔ 目录 `YYYYMMDD-<t>NNN-slug`，机械可互推（正面样板：35/35 零错位）；
   - 迁移 `NNNN-YYYYMMDD-slug.sql`，全局序号定执行顺序；
   - 用例 `TC-<模块>-NNN`（无版本段；如 `TC-UNION-PAYMENT-001`）；
   - 报告等记录类文档 `YYYYMMDD-<slug>.md`（slug 为 `[a-z0-9.-]+`，如封板测试报告 `20261010-test-report-v2.3.1.md`）；发布文档 `vX.Y.Z.md` / `vX.Y.Z-delivery.md`；包名 `vX.Y.Z-YYYYMMDD-HHMMSS-dist.zip`；
   - 取号规则：查所有并行分支与 worktree；撞号时后占方搬移、内容不变、注明原号；
   - 反面：#3、#14。
5. 机制 3 变更 bundle：四件套各答一问（要什么／打算怎么做／实际怎么做／怎么证明）；可选件（impact-map、handoff、manual-test-cases、review、stage 分册）何时需要、阅读顺序；轻量变更形态。反面：#8、#16。
6. 机制 4 主索引 + 派生视图：薄索引只回答「去哪读」不回答「是什么」；派生视图由脚本生成。反面：#5–#7。
7. 机制 5 状态机 + 替代链 + 归档：每个状态对应 Agent 的使用方式；`Replaced by` 强制跳转；「归档」只指被替代的历史（如被新 runbook 替代的旧手册），不指「做完的变更」——做完的变更原地不动，状态写在元信息里。反面：#1、#2、#13。
8. 机制 6 稳态规则 vs 存量接入：新项目第一天就按稳态规则建档，没有冻结区、没有日期特例、基线为零；中途接入的老项目才需要「接入三件套」——冻结区（旧格式文档只读，目录名只表示旧格式、不表示已完成）、规则生效日期、豁免基线（只降不升），且集中在一份接入配置里，规则正文和检查代码中不出现任何日期常量或历史路径。稳态目录结构：`plans/` 下只有主索引、直接平铺的 bundle（`YYYYMMDD-<t>NNN-<slug>/`，靠名字模式与 `tracks/` 区分）与 `tracks/`——不套 `changes/` 一层：它只为与冻结区区分而存在，且「change」按字面是「修改」，新项目的第一个功能并不是修改（按字面执行的 Agent 会被名字误导，与 `legacy` 同理）。存量项目若该层级已被大量引用（源项目 73 个文件 564 处、13 份已执行迁移 SQL 注释不可改），作为接入件「历史目录层级」保留，由接入配置声明 bundle 根目录。反例：源项目把 `legacy/YYYYMM/` 画进了通用层的「推荐目标结构」（#19），以及读者自然会把 `legacy` 误读为「已完成归档」——源项目 `legacy/202504/` 里唯一一份文件名就是「…后续再做」。
9. 机制 7 模板 = 文档内寻址：目录与编号解决「文档在哪」，模板解决「信息在文档的哪一节」——Agent 按固定章节名直接跳读，不必通读。一种文档一个模板、放同一处；模板头注释声明适用路径与必含字段，模板 H2 即必备章节，**模板本身就是 lint 规则**（不另维护规则清单）；禁止仿写上一份。反例（§5.3「仿写漂移」）：交接说明漏 SHA-256、回滚章节连续 8 版缺失、测试报告章节数 3–8 漂移；规范里「模板照 v2.0.2」一句本身就是仿写指令。会怎么坏：模板过严逼 Agent 填空话（对策：必备章节最少化、其余标「（可选）」，允许模板外章节）。
10. 跨类型对照表：放哪、命名、编号、事实源、派生视图、**模板**、人的角色。
11. 治理前后对比（治理落地后补真实数据）。
12. 小结。

### ④ 《让文档不烂——Agent 时代的文档生命周期（四）》

1. 开场：体系自身在腐化——状态 9 种写法、f005 撞号、索引段落化、深层断链 515；这些文档大多是 Agent 照规范写的：Agent 作者也会失忆。
2. 原则：写回是变更的一部分（完成定义包含文档回写）；约定由机器强制，人只裁决；入口层零容忍，深层设基线且只降不升。
3. 机制 1 写回闭环：「变更类型 → 必须回写到哪」表（实施回填、用例提升全局索引、handbook、用户手册、移动端评估、索引状态、roadmap）。反面：手册滞后 8 天；#16。
4. 机制 2「实案 → 立规 → 检查项」流水线与强制力阶梯：叙事 < L0 一句话规则（带日期和链接）< L1 细则 < review 检查项 < 共享 helper / 自动校验。例：下载接口 magic header 已到代码强制；迁移取号仍是人工规则。
5. 机制 3 doc-lint：编号唯一、词表合法、bundle 已登记、元信息完整、链接（入口 0／深层基线）；派生视图由脚本生成。**强制点不用 hook / CI**（源项目已明确不做 CI 卡点和 pre-commit）：路由表一行「改 docs/ 后提交前跑 doc-lint」+ 封板 checklist 加「doc-lint 0 违规」门禁。讲「Agent 是作者时，不靠 hook 怎么强制」。治理核心产出。
6. 机制 4 记忆分层：个人 memory 只放协作偏好，通用教训进 repo（#11）。
7. 机制 5 新鲜度：「当前事实」文档带 `Last reviewed` 与过期检查；顶部横幅滚动保留最近 N 条，其余归实现记录与 L3 执行报告（release 两件是交付物，不收横幅）（#15）。
8. 人的裁决点：批准 plan、拍板、封板验收、确认交付物。
9. 治理实录（治理落地后写）：D 类变更全过程与前后数据。
10. 跨类型对照表：写回触发／写到哪／谁强制（lint / review / 人）／人的角色。
11. 会怎么坏：lint 规则本身过期；过度强制逼 Agent 绕路，需留例外通道。
12. 系列收尾，链接 skill。

### 5.5 治理过程中暴露的问题（④篇「体系自己也会烂」素材，均有提交或评审记录可查）

> 这些发生在「用 Agent 做文档治理」的过程里，说明连治理本身也需要被检查。叙述一律中性：只写文档、提交、评审记录能证明的事。

1. **计划里给定的代码把项目历史写进了通用工具**：任务评审发现 doc-lint 的词表里带着本项目的旧状态/类型映射表（`completed`→`verified` 等），继承对也写死了本项目路径；用户裁决后分别移入一次性迁移脚本和项目配置 `baseline.json`（治理分支提交 `0a1125a3b`、`49b4e7d60`）。「通用规范」与「项目历史」的边界要靠评审才守得住。
2. **迁移计划先在真实数据上演练**：把计划里的代码抽出来在仓库副本上跑，审批前发现 5 处缺陷——截断「下一步」文字时切进 Markdown 链接产生新断链；索引导语不以 `> 20` 开头被横幅检查漏掉；补登标题重复 ID 前缀；一个测试漏传接入配置；9 个旧格式 Case ID（改为配置豁免而不改名）。演练前 308 个 ERROR（当时版本的工具），演练后 0。
3. **一条错误口径沿「入口文件 → 个人记忆 → 新文档」一路传播**：原入口文件写「dev = 用户口径的『线上 / 真实数据』」，实际三环境是 dev（62 内测）/ test / prod（集团生产，须 VPN）；这句话被原样搬进新建的开发环境文档（逐字搬移保证没丢规则，也保证没丢错误），评审发现、用户纠正后在仓库与个人记忆两处同时改正（治理分支提交 `e690a2ffa`）。教训：**「原样搬移」会无差别地搬走事实错误**，搬移前后各要核一遍事实。
4. **过时的记忆差点被迁成「当前事实」**：个人记忆里「OCR 无服务器、刻意不接入」一条，实施 Task 8 时核对代码与路线图发现正式环境早已接入 GPU OCR；该条未迁入而直接删除，并在迁移流程里新增「先核实是否仍成立」一步（治理分支提交 `acdc9de13`、`559fe9607`）。迁移 21 条记忆时，其中 4 条经核对为「部分过时」，只迁入仍成立的部分。
5. **模型凭注释推断出一个并不存在的缺陷**：评审发现保存接口的 javadoc 写「在途仅当前办理人」而实现放行创建人，被记为「疑似缺陷待裁决」；用户指出详情页点「通过」前会先调用该保存接口、不能收紧，补查调用链与 2026-08-20 的修复记录后撤回判断，文档改为「javadoc 比实现窄，以代码为准」（治理分支提交 `d8d915c1b`）。教训：**注释不是事实源，调用链才是**。
6. **终审发现计划里写的合并步骤会失败**：计划规定「合并 develop 时取其索引并重跑迁移脚本」；终审在临时 worktree 模拟，发现脚本会因 4 行列数错位中止、即使绕过也会丢掉治理变更的索引行并改回状态；改为手工吸收（治理分支提交 `eb2fd2bed`）。**一次性迁移脚本不可重跑**，要在文档里写明。
7. **检查工具自己的误报**：链接检查器原先不跳过代码块，治理计划自己的示例链接被误报 58 条，存量文档误报 12 条；模板检查最初按正文字样跳过「生成视图」，把提到该命令的设计文档整份漏检；用治理前的旧检查器量治理后的树会得到 638（误报），新检查器是 521。**工具本身也要被测试**，而且最好用自己的文档去检查自己（dogfooding）。
8. **规范落地后的第一份新文档仍沿用旧格式**：v2.3.2 的更新日志与交接说明在 2026-10-15 09:49 提交到主开发分支（`9fd42a5ac`），治理合并在同日 10:20（`88d1a6117` / !1302），**相隔约 30 分钟**；写这份文档时主开发分支上还没有 doc-lint 与模板，所以它既不能说明「没有 hook 就会漏」，也不是谁违规，只是「规则合入前就开着的工作，合并时才撞上新规则」。合并时按模板补章节才通过检查。没有模板时 Agent 只能仿写上一份，而上一份就是旧格式。
9. **脱敏词表自己泄露**：写博客系列的计划时，把整份脱敏词表和真实配置名作为测试样例写进了入库文件，终审发现；处理为：词表只存不入库目录、测试样例运行时拼接、检查脚本新增全仓扫描（含提交信息）、并重建仓库历史（旧历史仅本机备份）。教训：**「禁止出现的词」的清单本身就是敏感信息**。
11. **「只减不增」的约定没有工具强制**：模板豁免清单设计上只减不增，但合并 develop 时因并入规则生效前的存量文档加了 4 条（315→314→318），提交信息说明了原因；检查工具不核对清单只减不增，也不报告清单里已失效的条目（审查记录的 Minor）。约定写进规范只是第一步。
10. **迁移时核实出一个工具缺陷**：迁移记忆时发现开发辅助的数据库查询接口同一条 SQL 换 schema 参数会返回首个库的结果；先怀疑数据库按文本复用计划，后用对照实验排除，定位到连接池的语句缓存（Druid 在每连接缓存数 > 0 时自动开启），改用普通 Statement 修复（develop `!1300`）。——本条属于「文档里写疑似→实验证实」的小插曲，④篇可点到为止。

**`doc-lint --release` 与新鲜度（2026-10-15 读源项目核实）**：普通模式下「复核日期早于最近一次发布」只是 WARN；封板模式（`--release`，封板 checklist 第 2 步）把项目概览与 roadmap 的过期升为 ERROR。roadmap 顶部日期横幅上限 5 块（`ROADMAP_BANNER_MAX`，规范 §7.2）；`doc-lint next-id` 取号、`gen-views` 重新生成两个用例视图。`Replaced by` 只检查「键存在」（`META_REQUIRED`），不检查已替代的文档是否真填了新编号、目标是否存在。magic header 下载校验有共享 helper，但使用它是可选的：e2e README 的 Code review 项允许手写校验，只要比对 magic header 字节，审查兜底。

## 7. 脱敏规则

- 项目称「某企业级支付审批系统」；可写领域（支付审批、BPM、合同/计量）和技术栈。
- 可写真实量级（§5.1）与真实实案（去掉可识别细节）。
- **不得出现**：公司/集团名、项目代号与仓库名、IP/端口与主机、账号/密码/密钥、人名与工号、内部系统名。
- 引用源项目文档片段时：保留结构，改写可识别的业务词与路径中的代号。
- 源项目本机路径与敏感映射只放 `local/`（已 gitignore）。
- Agent 工具名（Claude Code / Codex / Kimi）保留：多 Agent 协作是主题的一部分。

## 8. 写作顺序

1. ①② 篇写作，与源项目治理**并行**；
2. 源项目治理：在源项目按其规则建 D 类 bundle、登记索引、经用户批准后实施；**从 develop 另开 worktree**，不触碰源项目当前工作分支上的未提交改动；
3. 治理落地后写 ③④ 篇（含治理前后真实数据）；
4. 四篇定稿后提炼 `skill/`。

## 9. 风格约定

- 中文；每篇 5–6 千字；遵循 §3 统一结构。
- 每个原则标注对应的 Agent 特性（§2）。
- 对照表平等覆盖各文档类型，含「人的角色」列。
- 每篇都写「本机制会怎么坏」，不只报喜。
- 模板片段只放关键部分，完整模板留给 skill。

## 10. 不做

- 不做通用文档工具或站点生成；
- 不写成某个 Agent 产品的使用教程；
- 不在博客中复刻源项目完整文档；
- skill 不在四篇定稿前动工；
- **不讲测试方法论**（分层策略、全量纪律、e2e 技巧、验收证据标准）——留给测试专题系列；本系列只讲测试**文档**的分层、寻址与索引。

## 11. 开放问题

- 源项目 overview 中移动端「正式 APK 随版本发布」与「永远只出 debug 包」口径是否冲突——治理时与用户确认（#15）。
- 博客发布平台与 skill 的具体格式——四篇定稿后再定。
- 与测试专题系列的交叉引用方式（互链、共用素材库）——测试系列启动时再定。
