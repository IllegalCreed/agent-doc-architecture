# Shared layered documentation spec

> Status: approved
> Last reviewed: 2026-10-14
> Scope: the documentation system of a software project developed with AI collaboration.
> After you copy this into a project: `docs/overview.md`, `docs/roadmap.md`, the release-seal process, and similar documents are created **only when they have content**. Do not pre-create an empty document to silence a dangling reference. Write "none yet" instead.
> Project landing: <after copying into a project, change this to a link to the project-layer documentation model, for example `[project-layer documentation model](documentation-model.md)`>

---

## 0. Premise: the first reader of the docs is the agent

| Property of an agent | What it requires of the docs | The mechanism |
|---|---|---|
| No memory across sessions | Every session enters through the entry, and the entry must be a routing table | L0 plus the "operation → required reading" table |
| Context is limited and it costs | Tokens are the first cost. Drill in on demand | L0–L3 layering, a thin index |
| It follows the literal text and does not infer | Status, the replacement relationship, and the scope are written out | The state machine, `Replaced by`, the required-reading table |
| It can grep, glob, and run scripts | Names are pattern-matchable, metadata is parseable, rules are checkable | The numbering scheme, the metadata block, doc-lint |
| It is also the main author | A convention that depends on memory will drift. It has to be enforced by a machine | The checker, plus a fixed point where it runs |
| Several agents at once | A single entry. A general lesson goes in the repo, not in personal memory | The one entry file |

- Code, tests, and documents are equally important. The documents tell the agent how to write and where to write the result back. The tests prove it was written correctly.
- A person is the adjudicator, not the reader: approve a plan, decide, accept. What a person reads is the summary the agent produces for an adjudication point.
- One document serves one kind of reader. An index is for the agent, and it stays thin. Progress for a person is summarized by the agent or generated by a script.
- Deliverables (the user manual, the changelog, the delivery note) do not enter the agent's routing system. The routing table only records when each of them must be updated.

## AI Quick Path

When an AI is given a task to build, fix, refactor, or investigate, read documents in this order. Do not scan everything:

1. `docs/README.md`: pick the single entry by the document's duty;
2. `docs/overview.md`: confirm what the system is and where its boundary is;
3. `docs/roadmap.md`: confirm the current stage, the milestones, the priority, and the risks;
4. `docs/plans/index.md`: locate the related plan by Type, status, module, title, and next step;
5. The related bundle's `requirements.md`: confirm the requirement, the boundary, and what not to do;
6. The related bundle's `design.md`: confirm the intended implementation;
7. The related bundle's `implementation.md`: confirm what actually landed, the deviations, the verification, and the leftovers;
8. The related bundle's `test-cases.md` and `docs/testing/cases/index.md`: confirm test coverage and stale status;
9. `docs/reports/`: drill in only when you need evidence, a log, an audit output, or a test report.

If `docs/plans/index.md` or the document metadata says `superseded` or `obsolete`, follow `Replaced by` to the new document before you do anything else.

## 1. Why this spec exists

In a project that uses AI-assisted development heavily, the main cost of the AI is not "reading one long document". It is:

1. Not knowing which document to read first;
2. Reading a stale plan and taking it for current fact;
3. Not being able to find which requirement a test case came from;
4. A change breaking an old feature, and the old feature's document and the global test index not being written back;
5. The implementation drifting from the original requirement, with the drift living only in a chat or a commit.

So the documentation system has to be layered:

- **The index layer stays thin.** It only tells the AI "what the state is now, and where to read next".
- **The plan layer is complete.** It states each change's requirement, design, actual implementation, and verification.
- **The evidence layer is traceable.** Test reports, SQL backups, audit CSVs, and the like are evidence of fact. They are not an entry point.

One sentence: **global documents navigate, plan documents decide, implementation documents record the fact, and the test index stops drift.**

## 2. Top-level document structure

The recommended target looks like this:

```text
docs/
├── README.md                           # Documentation entry and placement rules
├── overview.md                         # Project introduction: what the system is, its boundary, its main modules
├── operation-manual.md                 # User manual: how a business user operates it today
├── roadmap.md                          # Global roadmap: the current stage, milestones, important entries
├── handbook/                           # Long-lived notes on development, database, frontend, and the domain
│   └── templates/                      # One template per document kind
├── testing/
│   ├── guides/                         # The current testing spec and execution discipline
│   └── cases/                          # The global case registry and its views
├── deployment/                         # Runbooks that can be executed today: deploy, upgrade, operate
├── plans/
│   ├── index.md                        # The change-plan main index (the only status projection)
│   ├── YYYYMMDD-<t>NNN-<slug>/         # One bundle per change, laid out flat; a finished change stays where it is
│   └── tracks/<topic>/                 # Long-lived topics: navigation across several independent changes
├── reports/                            # Execution evidence: tests, audits, incidents, migrations
└── releases/                           # Version notes, upgrade notes, and artifact receipts
```

Short-lived and long-lived: **a bundle is short-lived** — one deliverable change, including a large change with several stages (one bundle plus `stages.md`). **A track is long-lived** — navigation for a topic that spans several independent changes. It records only why, the order, the boundary, and links to the related bundles. A track **does not hold a plan and does not record status**: an item in it is either already a bundle (read progress from the bundle's metadata) or has not started (it appears only in the navigation, and the bundle is created when it starts). Maintaining status marks inside a track creates a second source of status.

A bundle directory is distinguished from `tracks/` by the name pattern `^\d{8}-[a-z]\d{3}-`. A script, a service config, or a dashboard that can be deployed is a runtime artifact. It lives in the deployment directory at the repo root, and `docs/deployment/` links to it. Do not put executable source under `docs/` because it is convenient to explain.

### Where a subproject's documents stop

- System-level plans, deployment, incidents, execution reports, and exports all go into the duty directories of the root `docs/`. Do not keep a parallel documentation entry under a subproject.
- A documentation project a subproject needs in order to run (for example its own docs-site workspace) may stay co-located. It is not merged into the root documentation tree.
- A subproject may keep its own notes on how its tests are landed, but the root `docs/testing/` must provide the entry. The subproject document records only how it differs from the shared spec. It does not copy the shared spec.

### Change types and directory strategy

Every change is reached from `docs/plans/index.md`. The `Type` field is the semantic classification. Do not split different types into different physical directories.

Recommended types:

| Type | Recommended initial | Use |
|---|---|---|
| `feature` | F | A new capability, flow, page, or interface |
| `bugfix` | B | Fix a defect in existing behavior |
| `refactor` | R | A structural change. External behavior does not change, in principle |
| `test-infrastructure` | T | Test framework, fixtures, CI, a coverage catch-up |
| `docs` | D | Documentation rules, architecture notes, documentation governance |
| `ops` | O | Deployment, environments, operations, monitoring |
| `release` | C (from "cut"; the letter is whatever `vocab.py` says, and it is not changed after it is defined) | Seal a release, produce a package, publish |

The project layer defines the initial-letter map, and it is not changed after that. A new ID's initial is decided by the Type at the time the record is created. A later change of Type does not change the ID. **Every change has the same mechanism for requirements, design, implementation, tests, and writing the index back.**

### The `docs/plans/index.md` main index

`docs/plans/index.md` is the current-plan entry that must be maintained. It is not a list of historical files. It is the AI's first lookup table: use the index to locate the plan that still needs to be read or moved forward, then drill into the plan's metadata and body.

The index stays thin. Only six columns are required. Completion, blockers, Owner, the latest update, and the replacement relationship live in the plan's metadata block, so they are not maintained in two places:

| Stable ID | Type | Title | Status | Next step | Plan |
|---|---|---|---|---|---|
| F-20260601-001 | feature | Example capability | in-progress | Add the L2 integration test | `20260601-f001-example/requirements.md` |

What the fields mean:

- **Stable ID**: a stable number. It does not change because a directory moved or a title changed.
- **Type**: taken from the type vocabulary.
- **Title**: one sentence on what problem this solves.
- **Status**: the state machine in section 3.
- **Next step**: the smallest action that can be carried out, for example "add the L2 test", "waiting on the interface", "write the old document back". A terminal status writes `-`.
- **Plan**: points at the bundle entry (`requirements.md`).

The index and the metadata must agree on Status and Type. **The metadata block is the only source of fact for status. The index is its projection.** Recommended shape:

```markdown
# Plans Index

One line of explanation.

| Stable ID | Type | Title | Status | Next step | Plan |
|---|---|---|---|---|---|

## Topic entries
```

Maintenance rules:

- When you create a plan, register it in `docs/plans/index.md` first, then write the four documents.
- When the status, the title, the next step, or the replacement relationship changes, update the main index in the same change.
- The top-level `docs/roadmap.md` may cite the main index. Do not copy the long detail of every plan.
- If the project also keeps views by Type, by module, and so on, they may only be derived from the main index (best generated by a script). They must not become another source of fact.

### Where testing sits in the spec

Testing is not a second main line beside the development documents. Testing is part of every change plan:

- The change's `requirements.md` states the acceptance criteria.
- The change's `design.md` states the test design.
- The change's `implementation.md` records the verification that actually ran.
- The change's `test-cases.md` records the cases this change adds, changes, keeps, or retires.
- `docs/testing/cases/` is only a global reverse index, so a test case can be traced back to the requirement and the reason for the change.

The `test-infrastructure` type is only for the test system itself, for catching up historical coverage, or for a cross-module testing effort. It does not replace the testing sections of an ordinary business change.

## 3. The state machine

Every plan document states its status explicitly. Do not write only "done". Write whether it still represents current fact.

### 3.1 Plan status

| Status | Meaning | How an agent uses it |
|---|---|---|
| `draft` | Under discussion | Background only. Not a basis for implementation |
| `approved` | A person has approved it; not implemented | May be used as a basis for implementation |
| `in-progress` | Being implemented | Write results back as you implement |
| `implemented` | Code has landed; verification is incomplete | Read the implementation record and the test record |
| `verified` | Implementation and verification are both confirmed (including a sealed release) | May be treated as current fact |
| `superseded` | Taken over by a newer change | Must follow `Replaced by` |
| `deprecated` | No longer describes current behavior, but still has historical value | Traceability only |
| `obsolete` | No longer valid | Not a basis for implementation |
| `cancelled` | Decided not to do | Not a basis for implementation. Read why it was cancelled |

Use one metadata block at the top of each bundle's `requirements.md` (required keys first, optional keys after):

```markdown
> Status: approved
> Stable ID: F-20260601-001
> Type: feature
> Created: 2026-06-01
> Last reviewed: 2026-06-01
> Replaces: none
> Replaced by: none
> Progress: 60%
> Blocked by: none
> Next action: Add the L2 integration test
> Related plans: none
> Related tests: TC-DOMAIN-CHANGE-001, TC-DOMAIN-CHANGE-002
```

### 3.2 Test-case status

A test-case status applies only to a case. It does not stand in for a plan status.

| Status | Meaning | How the AI uses it |
|---|---|---|
| `active` | Currently valid, and it should keep being maintained | May be used as a current testing basis |
| `stale` | Possibly out of date, not yet confirmed | Cannot be used as a conclusion directly. Check the owner plan |
| `deprecated` | Do not add a new dependency on it, but it still explains history | Traceability or migration only |
| `obsolete` | No longer valid. Do not run it, and do not use it as a current basis | Read why it was retired, and the replacement case |

### Mandatory rules

- When behavior changes, do not silently edit the old requirement into "what it is now". Add or update the matching plan, and mark `Replaced by` on the old document.
- When a later change affects a document, do not edit only the new plan. Write back into the affected old document's change log or affected-record.
- When a test case is retired, do not delete it. Mark it `obsolete` in the global test index, and name the change that caused it.

## 4. The four documents of a change plan

Each complex change is one bundle directory, laid out flat under `docs/plans/`, named:

```text
docs/plans/YYYYMMDD-<t>NNN-<slug>/
```

Example:

```text
docs/plans/20260601-f001-order-status-rules/
```

`<t>` is the lowercase initial of the Type. `NNN` increments from 001 for the same date and the same initial, so several changes on the same day do not share a name. The Stable ID is `F-20260601-001`, and it converts to and from the directory name mechanically. `<slug>` is a short English or pinyin name, so it is easy to search from a terminal. The title may use Chinese.

### 4.1 `requirements.md`

Goal: say in plain language why, what to do, what not to do, and where the boundary is.

It must contain:

- **Background**: why it started, the business problem, user feedback, or something a test found.
- **User stories / scenarios**: who needs this capability, and in what situation.
- **What to do**: described in the language of the business, with no code detail.
- **What not to do**: explicit exclusions, so the scope is not widened later by mistake.
- **Business rules**: rules that can be decided, such as status, amounts, permissions, time, and data scope.
- **Boundaries and exceptions**: empty values, duplicates, concurrency, insufficient permission, across organizations / tenants / workspaces, historical data.
- **Acceptance criteria**: what counts as done.
- **Open questions**: points not yet decided, each with an owner and a date.
- **Change history**: append a record when the requirement changes.

The most important part is not "what to do". It is "**what not to do**". An AI expands a feature on its own when the boundary is unclear.

### 4.2 `design.md`

Goal: give the AI implementation guidance at the level of the code.

It must contain:

- **Overall approach**: how backend, frontend, database, and tests are split.
- **Modules and files involved**: files or directories expected to be added, modified, or left untouched.
- **Interface design**: service interfaces, the API client, request and response, error codes.
- **Data design**: tables, columns, indexes, dictionaries, migrations.
- **Permissions and organizational boundaries**: roles, feature permissions, data scope, isolation by organization / tenant / workspace.
- **State machine / definitions**: enum values, aggregation rules, the lifecycle.
- **Compatibility**: historical data, old interfaces, a gradual rollout, rollback.
- **Test design**: which L1–L5 tests need to be covered.
- **Risks and alternatives**: why this approach, and which approaches were dropped.

A design document may still be edited before implementation starts. After implementation starts, a major design change must be recorded in the deviations section of `implementation.md`.

### 4.3 `implementation.md`

Goal: record how it actually landed, not repeat the design document.

It must contain:

- **The final change list**: grouped by backend, frontend, database, tests, and docs.
- **The files actually involved**: relative paths, preferably.
- **Deviations from the design**: where the work did not follow the design, and why.
- **Pitfalls and fixes**: the error symptom, the root cause, and what was done in the end.
- **Data changes**: migrations, patch SQL, backups, and how to roll back.
- **Deploy and restart requirements**: which services must restart, which caches must be cleared.
- **Verification record**: which commands ran, which tests passed or failed.
- **Leftovers**: say explicitly whether each one blocks release.

If the implementation conflicts with the requirement, the record in `implementation.md` is the fact, but you must go back and correct `requirements.md` or add a replacement plan. The two must not contradict each other for long.

### 4.4 `test-cases.md`

Goal: keep this change's local test cases, and let the global test index point back at them.

Recommended table:

| Case ID | Title | Layer | Type | Preconditions | Steps | Expected | Automation path | Status |
|---|---|---|---|---|---|---|---|---|
| TC-DOMAIN-CHANGE-001 | Key business-rule regression | L5 | regression | Data that already meets the precondition | Perform the operation that triggers the rule | The system blocks or allows it according to the rule | `path/to/e2e.spec.ts` | active |

Field notes:

- **Case ID**: a stable ID. It does not change with the filename.
- **Layer**: the layers defined by the current project's testing spec, for example L1–L5.
- **Type**: `unit` / `integration` / `e2e` / `regression` / `contract` / `manual`.
- **Automation path**: when there is no automation, write `manual`. Do not leave it blank.
- **Status**: `active` / `stale` / `deprecated` / `obsolete`.
- **Why it was retired**: if it is not active, name the change that caused it.

## 5. Extra requirements for special change types

Every change uses the four-document structure of section 4 by default. A different `Type` may add points to pay attention to. It does not have to change the directory structure.

### 5.1 The `refactor` type

A refactor is not "the cheap version of the documents". It also needs requirements, design, implementation, and tests. The emphasis is different: it must say extra about the impact surface and about the behavior that stays the same.

`requirements.md` must answer:

- What triggered it: a bug, complexity, a permission hole, a test-coverage gap, a performance problem.
- Why this is a refactor and not a business feature.
- Which existing features, pages, interfaces, and tests it affects.
- Which features must explicitly not change.
- Whether the user-facing manual has to change.
- How acceptance proves "the feature did not change" or "it changed only inside the expected range".

A suggested impact table:

| Affected object | Original document | Impact type | Expected behavior | Write-back required |
|---|---|---|---|---|
| Affected feature A | `docs/plans/.../requirements.md` | A definition or a structural change | The named behavior stays the same | Yes |

`design.md` must contain:

- A comparison of the old structure and the new one.
- The migration steps.
- Compatibility and the rollback strategy.
- How the impact surface is verified.
- The test cases to add, change, or retire.
- Whether it needs to ship in stages.

`implementation.md` must contain:

- The actual change list.
- Whether the affected feature documents have been written back.
- Whether the global test index has been updated.
- Which tests the refactor retired, replaced, or added.
- Deviations from the design.
- The verification result.

`test-cases.md` lists the regression tests as well as the new tests:

| Case ID | Source feature | Purpose | Status | Notes |
|---|---|---|---|---|
| TC-DOMAIN-CHANGE-001 | Feature A | Stop the key business rule from regressing | active | Kept after the refactor |
| TC-OLD-001 | The historical implementation | Replaced by the new design | obsolete | Retired by F-20260601-002 |

A large refactor may add `impact-map.md`:

If a refactor affects more than 3 features, more than 10 test cases, or more than one subproject, add `impact-map.md` and keep the impact matrix there. A small refactor does not have to add a fifth document. That keeps the document count from growing.

### 5.2 The `bugfix` type

A `bugfix` must also record:

- The reproduction steps.
- The expected behavior and the actual behavior.
- The root-cause analysis.
- The smallest fix.
- A test case that stops it coming back.

### 5.3 The `test-infrastructure` type

A `test-infrastructure` change must also record:

- Which test layers, modules, or CI flows it affects.
- Whether it changes test data, fixtures, environment isolation, or how reports are defined.
- Whether it is a catch-up of historical coverage.
- If the thing being covered already has a change plan, link that plan.
- A new Case ID must be registered in `docs/testing/cases/` at the same time.

## 6. The global test-case index

Location:

```text
docs/testing/cases/
```

Purpose: from a test case, look back to the requirement, the plan, the reason for a refactor, the automation file, and whether it is currently valid.

The global test-case index is one main index and two view indexes:

| File | Dimension | Use |
|---|---|---|
| `docs/testing/cases/index.md` | Main index | The fact fields: Case ID, owner plan, automation path, status, last verified, and the rest |
| `docs/testing/cases/by-layer.md` | Test layer | Find cases by the project's test layers, for example L1–L5 |
| `docs/testing/cases/by-module.md` | Module, milestone, or focused effort | Find cases by business module, system module, milestone, or testing effort |

The two views are orthogonal. The same Case ID must be findable both by layer and by module, milestone, or focused effort.

The header the checker requires is the nine columns of the case-index template. Recommended rows:

| Case ID | Title | Feature / module | Owner Plan | Layer | Automation path | Status | Last verified | Notes |
|---|---|---|---|---|---|---|---|---|
| TC-DOMAIN-CHANGE-001 | Key business-rule regression | Feature A | `docs/plans/20260601-f001-...` | L5 | `path/to/e2e.spec.ts` | active | 2026-06-01 | - |
| TC-LEGACY-001 | Old-implementation compatibility case | Module B | `docs/plans/20260601-f002-...` | L2 | `path/to/test` | obsolete | 2026-06-01 | Replaced by the new design in F-20260601-002 |

The Notes column is where a case that is not active records why it was retired and what replaced it.

### Rules for the two dimensions

- **Case ID is the only primary key.** The same case uses the same Case ID in `index.md`, `by-layer.md`, and `by-module.md`.
- **The main index holds the facts.** Status, owner plan, automation path, and last-verified time come from `index.md`.
- **The layer index answers "which layer still needs a test".** Organize it by the layers the project testing spec defines, for example unit, integration, component, end to end.
- **The module index answers "what this module covers".** Organize it by business module, system module, version milestone, or testing effort, in line with the project's own testing roadmap.
- **A case belongs to exactly one primary layer.** That keeps layer counts from double-counting. If an end-to-end case depends on integration-test data setup, it is still classified as end to end.
- **A case may belong to more than one module.** A business flow that crosses modules may appear in more than one place in `by-module.md`. It must not be given more than one Case ID.

### Status rules

| Status | Meaning |
|---|---|
| `active` | Currently valid, and it should keep being maintained |
| `stale` | Possibly out of date, not yet confirmed |
| `deprecated` | Do not add a new dependency on it, but it still explains history |
| `obsolete` | No longer valid. Do not run it, and do not use it as a current basis |

### When an update is mandatory

The global test index must be updated when:

- An automated test is added.
- A test file is deleted or renamed.
- A change in the business definition makes an old assertion no longer true.
- A refactor makes a batch of tests no longer apply.
- A manual test becomes an automated test.
- A test failure is confirmed to be a requirement change, not a bug.
- A case's layer, or its module, milestone, or focused effort, changes.

## 7. The global roadmap

`docs/roadmap.md` is the only default roadmap. It answers where the project is now, what is next, and where the important entries are. It may cite `docs/plans/index.md`. It does not copy the long detail of every plan.

The global roadmap keeps only:

- The current picture of the project.
- The large stages, the milestones, and the cross-cutting tracks.
- The important milestones.
- Entry links.
- The current priority, dependencies, and risks.
- High-level conclusions that are still valid.

It does not hold:

- A commit-level log.
- The full analysis of a single bug.
- A large number of test steps.
- The detail of an old requirement that has been replaced.

A recommended way to cite:

| Milestone | Goal | Related plan | Status | Risk |
|---|---|---|---|---|
| M1 | An example milestone | `docs/plans/index.md#c-20260601-001` | in-progress | Depends on an external interface being confirmed |

`docs/plans/` does not get its own `roadmap.md` by default. If the project really needs a topic roadmap, for example "the large-migration roadmap" or "the testing-system roadmap", name it and state its purpose in the project-layer documentation model, so it does not overlap the global `roadmap.md` or `plans/index.md`.

## 8. Cross-link rules

So the AI can drill in at a low token cost, every link is maintained in both directions.

### A change affects an old feature

The new change plan:

```markdown
> Replaces: docs/plans/20260501-f003-old-rule/requirements.md
```

The old feature plan:

```markdown
> Status: superseded
> Replaced by: docs/plans/20260601-f001-new-rule/requirements.md
```

### A structural change affects a feature

The change plan writes:

```markdown
## Impacted Features

| Feature | Impact | Required doc update |
|---|---|---|
| Feature A | The key business-rule definition changed | requirements + test-cases |
```

The affected feature document writes:

```markdown
## Change Log

- 2026-06-01: Affected by F-20260601-002. The key business-rule definition moved from the old rule to the new rule.
```

The global test index writes:

```markdown
| TC-DOMAIN-CHANGE-001 | ... | active | ... | Still valid after F-20260601-002 |
| TC-DOMAIN-CHANGE-OLD-001 | ... | obsolete | ... | Retired because the definition changed in F-20260601-002 |
```

## 9. How the AI reads

When an AI is given a task, read in this order:

1. `docs/overview.md` or `docs/roadmap.md`: confirm the project and the current stage.
2. The project-layer documentation model: confirm the documentation rules.
3. `docs/plans/index.md`: locate the related plan by Type, status, completion, module, and summary.
4. The related change plan's `requirements.md`: confirm the requirement and the boundary.
5. The related `design.md`: confirm the intended implementation.
6. The related `implementation.md`: confirm what actually landed, and the deviations.
7. `test-cases.md` and `docs/testing/cases/index.md`: confirm test coverage and stale status.
8. `docs/reports/`: drill in only when you need evidence, a log, or an audit output.

The AI should not start by scanning all of `docs/reports/` or every historical plan. The index layer has to tell the AI which documents are worth reading.

## 10. Where documents are updated in the development flow

### 10.1 A new change

1. Register the change ID, Type, summary, initial status, and owner in `docs/plans/index.md`.
2. Create the change-plan directory.
3. Write `requirements.md` first, and state what to do and what not to do.
4. Write `design.md`. Develop after it is confirmed.
5. Keep writing `implementation.md` back while developing.
6. Add or update `test-cases.md`.
7. Update `docs/testing/cases/index.md`, `by-layer.md`, and `by-module.md`.
8. When the status, the completion, or the replacement relationship changes, update `docs/plans/index.md` in the same change.
9. Update `docs/roadmap.md` and `operation-manual.md` when they need it.

### 10.2 Changing an existing feature

1. Decide whether the behavior changes.
2. If the behavior changes, add a change plan, or append a change record to the plan that is still active.
3. When an old requirement is replaced, mark it `superseded`.
4. Update the status of the matching test cases.
5. Write the global test index back.
6. Update the status, the completion, and the replacement relationship in `docs/plans/index.md`.

### 10.3 A `refactor` change

1. Create a change plan, and set `Type: refactor` in the metadata.
2. In `requirements.md`, state which features are affected and which behavior does not change.
3. In `design.md`, write the migration strategy and the regression-test strategy.
4. After implementation, check off "feature documents written back" and "test index written back" in `implementation.md`.
5. Update `docs/plans/index.md`. If the global stage, a milestone, or the priority is affected, also update `docs/roadmap.md`.
6. Mark a retired test `obsolete`. Do not delete it.

### 10.4 A `test-infrastructure` change

1. Create a change plan, and set `Type: test-infrastructure` in the metadata.
2. It applies to test infrastructure, catching up historical coverage, and a cross-module testing effort.
3. If the thing being covered already has a change plan, link that plan from the testing-effort document.
4. If the catch-up finds that the original feature's requirement is out of date, write the original feature document back, or add a replacement plan.
5. A Case ID added by the catch-up is also written to `docs/testing/cases/index.md`, `by-layer.md`, and `by-module.md`.
6. When the effort is done, record the stage status and the entry only in the top-level `docs/roadmap.md` or in the topic roadmap the project layer names. Do not copy every test detail.

### 10.5 The project-layer documentation model

This spec is the shared base. Each project records that project's naming and layering choices in its own project-layer documentation model (for example `docs/handbook/engineering/documentation-model.md`). It does not rewrite the shared spec.

The project layer should state:

- The names of the test layers, for example L1–L5, unit/integration/e2e, or another layering the project defines.
- How modules and milestones are divided, for example by business domain, version, iteration, stage, epic, or system module.
- The map from Type to the ID initial, and the command that takes the next number.
- The naming rule for an owner, for example a team, a business domain, a service name, or a code owner.
- The entries for this project's user manual, deployment runbook, and operations runbook.
- The onboarding config used when the project adopts the rules partway through (see section 13).

## 11. Checklist before a PR or a commit

Before committing a change, check at least:

- [ ] There is a matching change plan.
- [ ] `docs/plans/index.md` records the summary, the status, and the completion.
- [ ] The requirement boundary says what not to do.
- [ ] The actual implementation was written back to `implementation.md`.
- [ ] A place that does not match the design has an explanation.
- [ ] A test that was added or changed is written in the local `test-cases.md`.
- [ ] The global test index `index.md`, `by-layer.md`, and `by-module.md` were updated together.
- [ ] A retired old test records the reason and the replacement.
- [ ] An old feature document that was affected was written back.
- [ ] Type, status, completion, and the replacement relationship in `docs/plans/index.md` were updated together.
- [ ] Whether the user manual needs an update.
- [ ] The roadmap keeps only the index and is not stuffed with implementation detail.

---

## 12. Common anti-patterns

Avoid these:

- Putting every detail into `docs/roadmap.md`, so the AI has to read a huge document every time.
- After a new requirement replaces an old one, editing the old document into the new definition and losing the historical reason.
- A test case that exists only as a test filename, with no Case ID.
- Deleting a stale test without writing why it went stale.
- A `refactor` plan that only says "clean up the code" and does not say which existing features it affects.
- An implementation document that repeats the design document and does not record the actual deviation.
- "TODO, fill in later" with no date, no owner, and no trigger.
- A document whose status sits at `in-progress` long after the code has merged.

## 13. Onboarding an existing project (a new project skips this section)

A project that files documents to this spec from day one has no "documents from before the spec took effect". Under plans there is only the main index, the bundles laid out flat, and `tracks/`. There are no exemptions, and the check baseline is zero. Only a project that adopts the rules partway through needs the pieces below, and they are all written in one onboarding config (for example doc-lint's `baseline.json`). They are not scattered through the rule text or the checker:

| Piece | What it does | When it goes away |
|---|---|---|
| A frozen area (for example `plans/legacy/YYYYMM/`) | Holds the old-format documents from before onboarding. Read-only; nothing new is added. The directory name means only "old format". **It does not mean finished.** Work that still has to move forward must be registered in the main index | When a frozen document is touched, migrate it to a standard bundle and mark the replacement |
| The day the rules take effect | An object created before that day is exempt from that rule (for example the numbering initial) | Permanent, but it applies only to what already existed |
| The exemption baseline | The list and the counts of existing violations (naming exceptions, files outside the allowlist, the broken-link count) | It only goes down. Delete the matching entry when it reaches zero |
| A historical directory level (for example a bundle root of `plans/changes/`) | A directory level that was already cited widely before onboarding, where renaming costs more than it gains. The onboarding config declares the real path | Moves with a major migration, or stays permanently |

Outside the onboarding config, no exception may be drawn by a date or by project history.
