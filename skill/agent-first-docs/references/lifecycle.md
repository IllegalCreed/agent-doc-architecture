# 生命周期：让文档不烂

Agent 每次会话都是新的，文档只要有一处没跟上代码，下一个会话就会拿它当事实。烂的原因几乎都是：**没人规定写回，写回了没人检查，检查的规则本身没人测**。

## 写回闭环

每种「事件」对应一份必须被更新的文档。把这张表写进规范，并让路由表指向它：

| 事件 | 必须更新 | 谁来裁决 |
|---|---|---|
| 变更开始 | 建 bundle（`next-id` → requirements），主索引加一行，状态 `draft` | 人批准后改 `approved` |
| 实现中 | 状态 `in-progress`；`implementation.md` 实施记录、元信息（`Progress` / `Next action`） | — |
| 实现完成 | 状态 `implemented`；`test-cases.md` 登记用例；索引状态与下一步 | — |
| 验证通过 | 状态 `verified`；索引「下一步」写 `-` | 人验收 |
| 被新变更接管 | 旧变更 `superseded` + `Replaced by`；新变更 `Replaces` | 人确认 |
| 发现实现与文档不符 | 优先改文档回到事实；若是代码错，开 bugfix 变更并记录 | 人判断哪边错 |
| 发版 | 更新日志、交付说明、概览 / 路线图的 `Last reviewed`、封板测试报告 | 人签发 |
| 出现事故 | 事故记录（复现 / 根因 / 修复 / 回归用例）；规范漏洞补进规范并加路由行 | 人复盘 |

写回是**同一次提交**的一部分：代码合入时，对应文档已是新状态。

## 强制手段的梯度

从弱到强，选当前能做到的最强一级，不要只用「提醒」：

1. **规范里写**：Agent 可能读不到。
2. **入口文件路由表加一行**：每个 Agent 开工前必读；成本最低、覆盖最广。
3. **模板头注释**：把规则写进「新建文档时必然复制的文件」里。
4. **`doc-lint`**：机器检查结构、元信息、编号、索引一致、链接、模板章节。
5. **封板门禁**：`doc-lint --release` 0 ERROR 写进封板清单；概览 / 路线图过期在此升为 ERROR。
6. **CI**：有则挂；没有也不要因此不做 1–5。

检查工具本身是代码：词表、模板头、基线都会变，必须有单测（本 skill 的 `assets/scripts/doclint/tests/`）。

## 新鲜度

- 元信息 `Last reviewed` 记录「最后一次**核对内容**的日期」，不是最后一次编辑。
- 「当前事实」类文档（默认 `fresh_docs`：概览、路线图、handbook、测试指南、部署 README）必须有它，缺失是 ERROR；早于最近一次发布是 WARN；`--release` 下只有 `strict_fresh`（概览、路线图）升为 ERROR。**不按天数报错**。
- 仓库没有 tag 时比较不执行，`--release` 会给 `FRESH-NOTAG` INFO：封板清单第一步先打 tag。
- 路线图顶部横幅最多 5 块，超出的旧横幅归档；动态进度不要写进索引或总览。
- 文档与代码的一致性靠写回闭环 + 人的验收；`doc-lint` 能查结构，**查不了内容是否真的新**。

## 链接与引用

- 路径稳定是前提（决策 2），这样链接才不会因为状态变化而断。
- `check-doc-links` 只校验相对路径指向的文件是否存在，**不校验 `#锚点`**；`mask_fences` / `mask_code` 避免误报代码块中的示例链接。
- 迁移或搬移文件后必须跑链接检查；批量修链接别手改：一次性迁移脚本里 `import doclint.linkfix`，用 `rebase_links` 重算相对链接。
- 文档里提到「某个事实」时，链接到该事实所在的文档，而不是复述——复述就是第二份会变旧的拷贝。

## 记忆分层

| 层 | 放什么 | 位置 |
|---|---|---|
| 仓库 | 项目教训、规范、决策、坑 | 入口文件 / handbook / 变更文档（git 全员可见） |
| 个人记忆 | 协作偏好：回复语言、批准方式、对输出的口味 | Agent 的记忆目录 |
| 会话 | 当前任务上下文 | 不持久 |

发现某条个人记忆其实是项目通用教训 → 迁入仓库，删掉记忆。

## 人的裁决点（只有这几处）

批准 `draft → approved`；验收 `implemented → verified`；确认 `superseded` / `cancelled`；判断「实现与文档不符，哪边错」；签发发布；复盘事故。**其余全部由 Agent 起草、维护、写回，人不是文档的维护者。**

## 常见情形

- **通用层不必整份复制**：`references/general-model.md` 篇幅大且假设了完整体系（by-layer、roadmap、operation-manual 等）。小项目的做法：项目层文档模型自成一份，只写已采用的部分，在「例外 / 暂未采用」节列出暂不适用的章节；需要继承对时才复制通用层。
- **零散存量文件**（`notes.md` 之类）：不删不改。内容无法核实的，不要编进新文档，也不要当规则写进入口文件；在项目层文档里登记为「待人确认」。`TEMPLATE-NONE` WARN 是预期。
- **何时建变更文档**：小团队可用阈值——跨多个 PR、或影响数据 / 接口 / 流程、或需要人批准的，建 bundle；一两处改动的修复写进提交说明即可。阈值写进项目层文档模型。
- **封板清单放哪**：没有独立封板流程文档时，作为项目层文档模型的一节，路由行指向它；有了流程文档再迁过去。
- **人批准状态**：上面写回表是完整流程。小项目的简化路径：Agent 做完一件事后补建的变更，可直接记为 `implemented`（跳过 draft / approved），`Next action` 写「等人验收」；`approved` 与 `verified` 只由人的明确指令推进。

## 回答「该不该新建文档」的判断

1. 它是不是一次可交付的变更？ → 建 bundle（或轻量形态）。
2. 它是不是跨多个变更的长期主题？ → track（只导航，不放 plan 和状态）。
3. 它是不是某次执行的证据？ → reports / 记录类目录，文件名 `YYYYMMDD-<slug>.md`。
4. 都不是，只是「想写点什么」 → 先问它要回答哪个路由问题；回答不了就别建。
