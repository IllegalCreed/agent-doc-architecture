# 关键决策：证据与被否决的做法

SKILL.md 列了 10 条「不能省的决策」。这里是每条的来由——Agent 自己搭体系时，**没有这些证据就会选另一边**。证据来自一个企业级支付审批系统（800+ 份文档、3600+ 次提交）的真实演进，以及在空白项目上不带本 skill 跑出来的基线。

## 1. 稳定 ID + `next-id`

- **否决：只用日期前缀**（`20260101-fix-login/`）。同一天两个变更、或两个并行分支各开一个，就撞名或不可区分；Agent 也无法从目录名知道「这是什么类型」。
- **否决：自增序号**（`plan-017`）。并行分支各自取下一个号，合并时必撞。
- **做法**：`<字母>-YYYYMMDD-NNN`。类型字母让索引和目录可按类型扫读；`next-id` 扫描所有分支和 worktree 取号。撞号时后占方搬移。
- **基线观察**：不带 skill 的 Agent 在存量项目里沿用旧的 `YYYY-MM-DD-slug`，也不去查其他分支。

## 2. 做完的变更原地不动

- **否决：完成后移到 `archive/` 或 `done/`**。变更一旦被引用（用例、更新日志、其他变更的 `Related plans`），搬目录就断一批链接；Agent 还会为修链接去改一堆无关文件。
- **做法**：状态写在元信息里（`verified`），索引的状态列是投影。只有被替代的历史才进 `archive/`，且保留 `Replaced by`。
- **基线观察**：不带 skill 的 Agent 自己设计体系时，规则里直接写了「完成后 `git mv` 到 `plans/archive/`」。

## 3. 旧文档不删、不改写

- **否决：为了统一格式而重写旧文档**。重写会丢掉当时的决策语境；而且 Agent 重写时倾向「润色」，把已经不成立的结论改得像现在成立。
- **做法**：原样搬移；挪走的文字存进迁出记录（`migration-record`）。**搬前后各核一遍事实**——原样搬会连错误一起搬走，搬完不核对等于认可了错误。

## 4. 索引只回答「去哪读」

- **否决：索引里写进度、日期、长说明**。进度每次变更都要同步改两处，必然不同步；多行导语会撑大 L0/L1 的读取成本。
- **做法**：固定六列、限行宽、禁止日期横幅。状态以变更自己的元信息为准，`doc-lint` 检查索引是否与元信息一致。
- **证据**：源项目主索引治理前平均行宽 394 字符、最长 1128；治理后固定六列，平均 157、最长 227。膨胀的根因是「顺手在索引里补一句」。

## 5. 一种文档一个模板

- **否决：「参考上一份同类文档」**。每份文档都以前一份为样本，误差逐份累积——更新日志、测试报告、发布说明在源项目里就是这样逐版偏移的。
- **做法**：每种文档一个模板，头注释声明适用范围和必含 / 禁含项；这条头注释**就是**该类文档的检查规则，`doc-lint` 直接读它，不另维护一套规则。
- 新增文档类型的流程：先建模板，再写文档。

## 6. 过期按「早于最近一次发布」提示，不按天数

- **否决：`Last reviewed` 超过 N 天报错**。基线观察：不带 skill 的 Agent 设计的是 `last_verified` 日期字段 + 脚本检查；这类字段在检查压力下最容易被「只改日期不核对」刷新，制造假新鲜。
- **做法**：只对少数「必须随发布更新」的文档（概览、路线图）检查 `Last reviewed` 是否早于最近一次发布；日常是 WARN，封板模式（`--release`）才升为 ERROR。核对内容仍靠写回闭环（见 lifecycle）。

## 7. 不预写没有内容的文档

- **否决：一次生成「完整文档体系」**（5 份 guide + 概览 + ADR 全部先建骨架）。基线观察：不带 skill 的 Agent 在只有一份 notes.md 的空项目里，一次提交了十几份此类文档。空文档不提供事实，却会被 Agent 当成「已有文档」引用，并开始往里编。
- **做法**：只建当下有内容的；缺什么，等有事实再建。目录 README 的放置规则已经说明「将来放哪」。

## 8. 强制靠路由表里的一行 + 封板门禁

- **否决：靠 pre-commit hook / CI 强制**——并非不能用，而是源项目没有 hook 与 CI，却把 doc-lint 的 62 个测试和 36 种检查码跑成了日常纪律：**一行路由表**（「改 docs 后提交前跑 doc-lint」）让每个 Agent 开工前都读到，**封板清单**里 `--release` 0 ERROR 是最后一道。有 CI 的项目，在此之上挂 CI。
- **检查工具本身要被测试**：规则会随词表和模板演进，没有单测，改一处就会悄悄放过一类错误。

## 9. 入口文件每条 = 规则 + 理由 + 链接

- **否决：入口文件堆实案**。源项目入口文件曾 128 行 → 406 行 → 457 行，规则相互掩盖；一次封板漏写发布文档，规范其实早就有，但从入口不可达。
- **做法**：每条只留「规则 + 一句理由 + 链接」；多个 Agent 的入口文件只做转发，防两份各自生长。

## 10. 个人记忆只放协作偏好

- **否决：把项目教训记在某个 Agent 的个人记忆里**。其他 Agent、其他会话、新同事全看不到；换个工具就等于没记。
- **做法**：通用教训进仓库（入口文件或规范文档，走 git 全员可见）；个人记忆只存「这个人怎么协作」的偏好，如回复语言、批准方式。

## 附：几条被验证过的「不要」

- 不要用 `rm`/批量重命名做「一次性整理」而没有可回滚的提交边界——一次大整理应是一个可独立撤销的提交。
- 不要把人写成「读者」：人批准、拍板、验收；手册和更新日志是交付物，读者是业务方，不进 Agent 路由。
- 不要让索引、路线图、手册去追同一份「当前状态」——状态只在一个地方写，其他处是链接。
